7. APK/AAB, встановлення на телефон і публікація — окремі погоджені кроки. Мердж сам по собі не запускає збірку.

## Де змінюється версія

Узгоджено оновити:

- `app.json`: `expo.version` і `expo.versionCode` (якщо з'явиться `expo.android.versionCode`, перевірити його пріоритет у Gradle).
- `package.json`: `version`.
- `package-lock.json`: верхній `version` і `packages[""].version`.
- `CHANGELOG.md`: опис кінцевої зміни та її перевірок.

Android Gradle читає версію з `app.json`. Не змінювати залежності лише заради підняття версії. versionCode наступного оновлення має бути більшим за попередній. Номер версії у файлі не доводить наявність зібраного чи встановленого APK.

## Перевірки за обсягом

Наведені команди виконуються на Codex у корені StellarShift. Вибирати потрібні для конкретної зміни, а не запускати весь набір автоматично.

```bash
./node_modules/.bin/tsc --noEmit
npm run lint
node scripts/catalog-cache.test.cjs
node scripts/catalog-loading.test.cjs
node scripts/blocked.test.cjs
node scripts/rotation.test.cjs
git diff --check
```

На базі 4.0.10 ці чотири JS-файли дали 38 успішних тестів; lint мав 3 попередження React Hooks. Це історичний результат, а не автоматично успішний статус будь-якої наступної версії.

Для змін native-приховування є `bash scripts/test-blocked-native.sh`: потрібні JDK, Android SDK 36 та вже наповнений Gradle-кеш. Раніше пройшли 4 Kotlin-перевірки. Інші native-сценарії потребують своїх перевірок; компіляція не замінює телефон.

Для суто документаційного PR достатньо перевірити JSON версій, зміст diff, Markdown-посилання, збереження архівів та ідентичність двох Roadmap. Не запускати Android-збірку для такої перевірки.

## Робота зі збіркою після окремого погодження

- JS-зміни можна перевіряти через Metro з відповідною development-збіркою. Звичайний Expo Go не замінює збірку з власними Kotlin-модулями StellarShift.
- Зміни Kotlin/manifest/assets потребують нової native-збірки. Release APK містить JS-пакет і не потребує Metro.
- Перед збіркою звірити гілку/коміт/версію, залежності lockfile, SDK/JDK, вільну пам'ять і підпис. Не читати та не виводити паролі/приватні ключі без потреби.
- Використовувати наявний production-підпис для оновлення встановленого застосунку. Не генерувати новий ключ замість старого лише через помилку конфігурації; секрети не включати в Git, Obsidian, PR чи діагностичний вивід.
- Для S23 Ultra раніше збирали ARM64. Перед наступним запуском погодити ARM64/universal та APK/AAB; відповідні команди й параметри перевірити на актуальному конфігу.
- Не запускати `clean`, оновлення SDK або паралельні важкі збірки як звичайний перший крок діагностики.
- Після збірки перевірити версію, versionCode, архітектури й сертифікат артефакту; записати шлях, розмір, SHA-256 та коміт. Окремо перевірити оновлення поверх встановленої версії зі збереженням даних і сценарії QA.

Перед реорганізацією 2026-09-24 оригінали шести нотаток і `_Coding MOC.md` зчитуються в локальну резервну копію. П'ять старих нотаток переміщуються в датований архів без зміни вмісту; кандидати доповнюються статусами без втрати посилань. Назви архівованих файлів зберігаються, тому старі wikilinks за унікальним ім'ям можуть продовжити їх знаходити; актуальний Coding MOC веде на нові документи.

Для відкату документації спочатку погодити обсяг і перевірити, чи немає новіших правок: повернути архівні нотатки та попередній MOC/список кандидатів із перевірених копій; нові документи перенести в окремий архів відкату. Git-зміну відкотити окремим PR. Не перезаписувати новіший вміст автоматично.

LAUNCH.md, RELEASE.md, STORE.md та history_speak.md збережені як історія. Їхні команди, політики, строки й припущення не використовуються замість актуального погодженого плану.
