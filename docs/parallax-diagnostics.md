# Діагностика ривків tilt-паралакса — 4.0.23

Мета: виміряти перехід від плавного нахилу до ступінчастого руху, який власник спостерігає приблизно через 10 секунд після повернення на робочий стіл Samsung S23 Ultra. Ця версія додає вимірювання, а не виправлення паралакса.

## Як працює запис

- Журнал Android `logcat`, тег `StellarParallax`, рівень Info. Доступний і в release APK.
- Після переходу шпалер із прихованого стану у видимий починається нова сесія. Повторне `visible=true` без приховування позначається окремо, але не подовжує сесію.
- Зведення приблизно кожні 2 секунди протягом перших 30 секунд. До 15 регулярних зведень за сесію; приховування або знищення двигуна завершує її з останнім частковим зведенням.
- Окремі записи показують зміну видимості, створення/знищення поверхні, успішність реєстрації датчика. `engine` — тимчасовий ідентифікатор екземпляра, `session` — номер сесії в ньому; це дозволяє розрізнити preview і робочі шпалери.
- Завершення за часом виконується при наступному кадровому callback. Якщо потік повністю завис, останнє зведення може прийти пізніше 30 секунд; фактичний час буде в журналі. Окремий таймер не запускається.
- У журналі немає фотографій, URL, ключів API, назв файлів, текстів винятків чи значень нахилу. Немає надсилання в мережу або окремих файлів журналу всередині застосунку.
- Форматування й запис виконуються лише для зведень та подій життєвого циклу; між ними накопичуються лічильники. Вплив діагностики на реальний телефон ще не виміряний.

## Отримання журналу через MobaXterm

Спочатку окремо зібрати й встановити 4.0.23. Жива шпалера StellarShift повинна бути активною. APK цією зміною не збирається.

Ці команди виконуються **на Codex**, якщо телефон уже підключений до ADB саме на цьому сервері:

```bash
adb devices -l
```

Якщо список порожній або статус `unauthorized`/`offline`, зупинитися: спершу окремо налаштувати та підтвердити ADB-доступ. Tailscale сам по собі не означає, що ADB підключено. Не відкривати ADB у публічний інтернет.

У наступній команді замінити `SERIAL` на ідентифікатор пристрою зі статусом `device`:

```bash
adb -s SERIAL logcat -v threadtime -T 1 'StellarParallax:I' '*:S' > /tmp/stellarshift-parallax-4023.txt
```

Команда працює до Ctrl+C. Вона не очищає системний журнал і записує лише обраний тег. Файл перезаписується при наступному запуску цієї самої команди, тому попередню потрібну спробу спочатку скопіювати.

1. Почати запис **до** відтворення проблеми.
2. Відкрити звичайні непрозорі «Налаштування» телефона на кілька секунд і повернутися додому. Це надійніший спосіб отримати приховування/показ, ніж меню програм, у якому шпалери можуть залишатися видимими.
3. Протягом 35 секунд плавно нахиляти телефон у схожому темпі. Не торкатися екрана в цей час, щоб не приховати можливий перехід після бездіяльності. Не змінювати яскравість, режим плавності екрана, енергозбереження, інтенсивність паралакса чи автозміну між порівнюваними спробами.
4. Записати приблизну секунду появи ривків. Окремо вказати версію Android/One UI, чи активні автозміна й енергозбереження, та налаштування плавності екрана.
5. За потреби повторити вхід/вихід зі StellarShift та такий самий 35-секундний нахил для порівняння.
6. Натиснути Ctrl+C у MobaXterm. Перевірити журнал:

```bash
wc -l /tmp/stellarshift-parallax-4023.txt
tail -5 /tmp/stellarshift-parallax-4023.txt
```

Завантажити `/tmp/stellarshift-parallax-4023.txt` через SFTP-панель MobaXterm і передати для аналізу. Очікуються `event=visible`, зведення `event=sample`, потім `event=capture_end reason=timeout` приблизно на 30000 мс. Порожній журнал не доводить відсутності проблеми: перевірити пристрій, установлену версію, активність живої шпалери й те, чи був перехід hidden → visible.

## Що означають показники

У полях `*_ms` формат **середнє/максимум/кількість спостережень**; `-` означає, що вимірювань немає. Інтервали між сусідніми подіями зберігаються через межі двосекундних вікон, але скидаються при новій сесії.

| Поле | Значення |
|---|---|
| `elapsed_ms`, `window_ms` | Час від початку сесії й фактична довжина поточного вікна |
| `frames`, `skipped` | Кількість кадрових callbacks і тих із них, де чинна логіка вирішила не малювати |
| `posted` | Успішні повернення з `unlockCanvasAndPost`; це не вимірювання фактичного показу кадру дисплеєм |
| `frame_gap_ms` | Інтервали між часовими мітками Choreographer |
| `callback_gap_ms`, `callback_delay_ms` | Інтервали між фактичними входами в callback і затримка входу відносно його кадрової мітки |
| `same_vsync` | Повторні callbacks із тією самою кадровою міткою; сигнал для перевірки дублювання циклу, а не готовий діагноз |
| `sensors`, `sensor_gap_ms` | Кількість подій датчика та інтервали між їхніми власними часовими мітками |
| `sensor_arrival_ms`, `sensor_age_ms` | Інтервали доставки подій та їхній вік у момент отримання |
| `lock_ms` | Час отримання Canvas, включно з очікуванням у `lockCanvas` |
| `draw_ms` | Повний час спроби малювання: lock, малювання й unlock/post; count включає й невдалі спроби |
| `reload_ms`, `reload_failures` | Час перечитування фото та кількість спроб, що не завантажили новий bitmap, включно з відсутнім файлом |

Кадрові часові мітки порівнюються з `System.nanoTime()`, датчик — із `SystemClock.elapsedRealtimeNanos()`. Ці дві шкали не змішуються. Джерела: [Choreographer.FrameCallback](https://developer.android.com/reference/android/view/Choreographer.FrameCallback), [SensorEvent.timestamp](https://developer.android.com/reference/android/hardware/SensorEvent#timestamp).

Порівнюємо вікна до та після видимого початку ривків. Самі ці числа не доводять зміну фізичної частоти дисплея або провину енергозбереження Samsung. За потреби наступним окремо погодженим кроком буде системне трасування. Після визначення причини тимчасову діагностику слід прибрати окремою погодженою правкою.

## Перевірки на сервері

```bash
bash scripts/test-parallax-native.sh
```

Використовує наявні Kotlin 2.1.20 у Gradle-кеші та Android SDK 36. Компілює реальний `LiveWallpaperService.kt` і лічильники; для стороннього `NotificationHelper` підставляє тільки константу імені файлу. Виконує JVM-тести лічильників зі штучним часом. Не запускає Android-сервіс, не збирає APK й не підтверджує поведінку Surface/SensorManager на телефоні.

## Порівняння з 4.0.24

Повторити той самий 35-секундний сценарій після встановлення 4.0.24. На S23 Ultra очікуємо `renderer=hardware` у події створення поверхні та `hardware_draws`, що відповідає кількості спроб із отриманим апаратним Canvas. Нові `render_ms` і `post_ms` відокремлюють малювання від `unlockCanvasAndPost`; `draw_ms` залишається повним часом. Це час CPU-викликів, а не вимір GPU чи фактичного показу дисплеєм. Додатково перевірити зміну фото з crossfade, блокування/розблокування й повернення з іншого застосунку без чорного фону. Плавність поки не підтверджена.
